## Reproducible read-only frontend promotion

1. Commit reviewed changes on the migration branch and keep the worktree clean.
2. Run `node scripts/build-vps-preview.mjs`. It builds from that exact commit,
   disables dotenv loading, pins the VPS API and read-only flags, checks for known
   private credentials, and writes a SHA-256 artifact manifest in the ignored
   local migration directory. The snapshot banner remains 6 November 19:33 WIB.
3. Copy the candidate to a new `/var/www/rhi/releases/preview-*` directory and
   upload the current infrastructure checker and promoter to `/opt/rhi/migration`.
4. From an external client, verify API order POST returns 409 and Kirimdev webhook
   GET returns 503. Store `checked_at` (ISO UTC), `commit`, `api`, `write_status`,
   `webhook_status` in a private JSON receipt and copy it to `/opt/rhi/migration`.
   The VPS's own address bypasses the Nginx external fence by design.
   Run `python3 /opt/rhi/migration/promote-preview-frontend.py CANDIDATE --external-proof RECEIPT` on the
   dedicated VPS. It verifies hashes, isolation, backup freshness, TLS and external
   fences; switches the frontend symlink; verifies served HTML and write denial;
   restores the previous symlink if post-promotion checks fail.
5. Repeat external HTTP fence checks, check browser rendering, and retain the
   private promotion receipt. No backend
   release, source write, webhook change, or operational cutover is performed.

## Coordinated cutover sequence

1. Resolve provider/account and scope gates above; verify the exact frontend
   commit and immutable backend bundle checksums intended for release.
2. Agree a staff input pause. Quiesce **all** source writers: staff, public forms,
   provider callbacks, schedulers and queued jobs. Preserve/replay pending events
   with idempotency; never discard them or run both delivery paths concurrently.
3. Take fresh recoverable source and target backups. Prepare/apply a consistent
   final delta only after verifying target preconditions. Check rows, deletes,
   relationships, Auth, sequence values, Storage metadata and actual file bytes.
4. Verify counts/hashes and critical workflows on the final target. Keep external
   writes fenced until parity and acceptance are recorded.
5. Move callbacks and scheduler ownership once; activate only the approved
   providers (Google Ads, TikTok Ads and Cekat remain excluded). Verify scheduled jobs cannot
   silently reactivate deferred providers after the final data sync. Install the reviewed writable
   frontend, open target writes in the agreed order, and keep source read-only.
6. Run authorized live delivery and login/order/upload/finance checks, inspect
   errors and queues, verify a fresh offsite backup, and record release evidence.

Before target writes begin, rollback can restore the prior preview/frontend and
source ownership. After target writes begin, pause writes and reconcile new target
transactions/events before any rollback. Blindly restoring an older database would
lose accepted transactions and is not an acceptable rollback procedure.
